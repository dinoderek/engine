# Session signals

> **Owns:** how a coordinator pass reads whether a session is alive and takes input, stalls, early deaths, limit recovery and deaths at a limit. **Not here:** dispatch, recovery of other ended attempts and the merge queue (`coordinator.md`), what each harness observes (`harnesses.md`), what a run records (`telemetry.md`).

Agent state is never scraped from the pane: task state and questions are server records. Two sources say whether a session is alive and takes input:

1. **The harness** gives each window of session `engine` a `state` (`working`, `waiting` or `limited`) from the observation of the harness its newest `run.json` names (`harnesses.md`). A window with no run included is unknown.
2. **tmux.** A window whose command has not exited is alive; a dead window is dead whatever the harness says.

A session is **idle** when `waiting`, or `working` with `background` set. Only idle sessions get wake-up pointers. A `waiting` window the harness marks `dialog` is held at a dialog typed input would answer, such as a trust prompt whose default exits: it is never idle, so nothing is typed into it, but its wait counts toward a stall, whose notice says to answer it in the window.

**Stalls.** Limited, queued and background-only sessions never stall. A dispatched session that has not claimed its task 5 minutes after it started is noticed once, and one that ended before claiming is an early death. A session waiting 10 minutes on an open task with no hard stop or question has stopped outside the protocol; the operator is notified once, naming the sign-in for a signed-out harness. A denial at most 10 minutes older than the wait makes the stall a Permission hard stop naming the tool, input and reason.

**Early death.** A window gone before its session claimed the task, which neither wrote to the server nor was seen live for `ClaimWait`, is not a vanish unless the vanish rule (`coordinator.md`, "Dispatch and recovery") already applies. The first such death per task, across attempts, ends the attempt `early-death` with its pane log tail recorded and, with a notice, returns a running task to `todo` for the next pass to redispatch. The second ends the attempt and task `failed`, and its notice carries both attempts' tails. Deaths of sessions that claimed never count; an early death after one is still the first. An operator's retry of a failed task counts the earlier early deaths, so one more fails it at once.

**A dead planner.** A planner whose window is gone, on an approved plan with no task, is ended. Its death counts as early, claimed or not: the first since coordination last started ends `early-death`, and the next pass starts a new planner as a resume, once the plan has no open question of its own; the second ends `failed` and stops coordination, its notice carrying both tails, and the operator's next run starts the count again. A death at a limit ends `vanished` and never counts, and only the first in a row tells the operator; the new planner waits for the reset plus 2 minutes, or 30 minutes when the reset is unknown. A planner ended after writing tasks ends `vanished`, and the plan goes on with its tasks.

**Limit recovery.** Never resume `needs-human`; recheck the task's state before typing. Once the reset plus 2 minutes has passed, each check sends `continue` into a window still `limited`, or `waiting` with a positive limit `resets_at` (Enter alone when the input line already holds unsent text, `tmux.md`). With the reset unknown, a window still `limited` gets one every 30 minutes from when it was first seen limited or its last continue, with no stuck notice; other sessions are left alone. The attempt is noted first, so a failed Enter never duplicates text. Waiting with a limit reset also clears the stall timer. Still `limited` 10 minutes after the attempt, or a reset over 24 hours away (no typing), gives one notice per reset and session. Recovery covers planners, executors and cleanup turns.

**Death at a limit.** A window gone or dead while its run's limit marker is set (`harnesses.md`) ends its attempt `vanished`, recording the limit and its reset, unknown if the marker has none. Only such a death, not a live limited session, puts the host × harness at a limit, until an attempt started there after it claims its task (`control.HarnessLimits`, derived from the attempts). Until then placement starts nothing there before the reset plus 2 minutes; with the reset unknown, one task every 30 minutes after the limit or the last probe, and none while one runs. Another host or harness may take the task sooner. On the same host it resumes on its own local branch; elsewhere only from what the branch has on `origin` (`hosts-and-sessions.md`). A session started there after the limit that is `limited` again before it claims is released at once, keeping its worktree and branch, and its death at the limit restarts the wait quietly; only the first death tells the operator, with when the task is dispatched again. After 12 hours of failed probes with the reset still unknown, one note.
